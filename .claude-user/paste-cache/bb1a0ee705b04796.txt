## Problem to fix

The current `PUT /api/export/todoist/settings` route uses this pattern:

1. Read the current settings row.
2. Merge a partial request body in JavaScript.
3. Upsert the merged object.

That creates a lost-update race when two updates occur close together:

```text
Current:
taskProjectId = A
eblastProjectId = B

Request 1 updates taskProjectId to C.
Request 2 updates eblastProjectId to D.

Both requests read { A, B }.
Request 1 writes { C, B }.
Request 2 writes { A, D }.

Result:
The update to C is lost.
```

## Required design

Replace partial-update semantics with full-document replacement semantics.

### API contract

`PUT /api/export/todoist/settings` must require both properties:

```ts
{
  taskProjectId: string | null;
  eblastProjectId: string | null;
}
```

Rules:

- Both fields are required in the request body.
- Each field may be `null`.
- An empty string from the existing Select UI must still normalize to `null` before validation/upsert.
- The route must not call `readSettings()` before a `PUT`.
- The route must perform one atomic singleton upsert using `id = "default"`.
- `GET` must remain unchanged:
  - Return `{ taskProjectId: null, eblastProjectId: null }` when no row exists.
- The response still returns the full saved settings document.

### Frontend context

Update `TodoistProvider` so each selector update always submits both current values:

- `setTaskProjectId(taskProjectId)` sends:
  ```ts
  {
    taskProjectId,
    eblastProjectId: currentServerOrCachedEblastProjectId
  }
  ```

- `setEblastProjectId(eblastProjectId)` sends:
  ```ts
  {
    taskProjectId: currentServerOrCachedTaskProjectId,
    eblastProjectId
  }
  ```

Requirements:

- Preserve the public context interface:
  - `taskProjectId`
  - `eblastProjectId`
  - `projects`
  - `loadingProjects`
  - `setTaskProjectId`
  - `setEblastProjectId`
- Preserve safe loading behavior: no selector write before server settings have loaded.
- Preserve `"" → null` behavior at the API boundary.
- Do not add optimistic updates unless the existing app pattern clearly requires them.
- After mutation success, keep updating the React Query settings cache with the complete server response.
- Do not retain or restore browser `localStorage["todoist_prefs"]`.
