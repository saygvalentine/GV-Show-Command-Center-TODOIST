## Delivery service requirements

Extract the existing per-item behavior from routes/todoist.ts into shared reusable functions for tasks and e-blasts.

The shared service must:

1. Preserve existing eligible-item behavior:
   - Dated task/e-blast → create or update a Todoist task.
   - Undated task/e-blast → no Todoist representation.
   - If an undated item has a linked Todoist ID, delete/unlink the remote task according to the existing manual workflow.
   - Preserve Todoist content/description formatting unless a clearly necessary defect is found.

2. Preserve completion behavior:
   - Task `completed` maps to Todoist close/reopen.
   - E-blast `sent` maps to Todoist close/reopen.

3. Correct the manual result counter:
   - Increment created only after a Todoist create response contains a valid remote task ID and the local mapping is persisted.
   - Do not claim a successful create merely because a create request was attempted.

4. Use the existing low-level Todoist client:
   - Keep `todoist-client.ts` as the only outbound HTTP/proxy layer.
   - Preserve its existing 429 retry behavior.

5. Handle 404 safely:
   - If an update of a previously linked Todoist task returns 404, clear the local todoistTaskId and preserve the local task/e-blast.
   - Do not recreate the Todoist task in the same delivery attempt.
   - Do not add any automatic-recreation-on-next-local-edit behavior in this PR.
   - Return a clear delivery outcome such as `unlinked` / `remote_missing` so future outbox code can apply the approved repair-only policy.
   - Do not invent a new database schema field or migration in this PR.

6. Make outcomes explicit:
   - Define typed delivery outcomes/counters for at least:
     - created
     - updated
     - completed/reopened as applicable
     - deleted
     - skipped_no_due_date
     - unlinked_remote_missing
     - failed
   - The manual route may continue displaying its existing result shape, but it must derive counts from real typed outcomes.

7. Do not add outbox behavior:
   - No todoist_sync_events insert/read/claim/retry code.
   - No automatic sync from ordinary task/e-blast CRUD.
   - No request-triggered retry sweep.
   - No timer or polling code.

## Testing requirements

Add backend unit tests with mocked Todoist HTTP/client behavior. No real Todoist account, connector, production DB, or production API calls are allowed.

Cover at minimum:

1. Dated task without todoistTaskId:
   - Todoist create succeeds with valid ID.
   - Local mapping update is requested/persisted.
   - Result is created.

2. Dated e-blast without todoistTaskId:
   - Same behavior as task.

3. Dated item with existing todoistTaskId:
   - Update is sent.
   - Result is updated.

4. Completed task / sent e-blast:
   - Upsert occurs, then Todoist close is called.

5. Reopened task / unsent e-blast:
   - Upsert occurs, then Todoist reopen is called.

6. Undated, unlinked item:
   - No Todoist call.
   - Result is skipped_no_due_date.

7. Undated, linked item:
   - Delete is called and local mapping is cleared.
   - Result is deleted/unlinked as appropriate.

8. Todoist 404 while updating a linked item:
   - Local mapping is cleared.
   - No create request is made afterward.
   - Result is unlinked_remote_missing.

9. Todoist create response without a valid ID:
   - Do not increment created.
   - Do not persist a false/empty local mapping.
   - Return failed or explicit invalid-response outcome.

10. Todoist non-429 failure:
   - Error/outcome is surfaced to caller without corrupting local mapping.
