## Goal

Renovate the existing manual one-way Todoist integration into an automatic, low-cost, two-way sync between Show Command Center and Todoist.

Normal desired behavior:

- Create/update/check off/reopen/delete a Show Command Center task or e-blast → synchronize the linked Todoist task automatically.
- Check off/reopen/delete the linked Todoist task → reflect the appropriate state in Show Command Center automatically.
- Do not rely on manual “Push to Todoist” buttons.
- Do not use frequent polling, since this runs on Replit and we want to avoid keeping the production database/process active unnecessarily.
- Use Todoist webhooks for normal inbound changes.
- Use immediate, targeted outbound calls after local changes.
- Keep only a low-frequency/on-demand repair/reconciliation capability as a safety net.

## Critical architecture amendment

The prior plan suggested a retry queue drained by a persistent `setInterval` inside the API server.

Do NOT use a continuously running or frequent in-process retry loop as the primary queue processor.

Instead, design a durable event/outbox model that:

- Records each outbound Todoist intent in the database atomically with the local mutation whenever possible.
- Supports operations including:
  `create`, `update`, `complete`, `reopen`, `delete`, and `unlink`.
- Has status, attempt count, next attempt time, idempotency key, payload snapshot, timestamps, and error details.
- Attempts delivery immediately as part of an already-active user request when safe.
- Retries only through cost-conscious triggers:
  - subsequent application requests,
  - webhook requests,
  - an explicit “Sync now”/repair action,
  - and, only if truly necessary, a low-frequency scheduled recovery job.
- Uses a safe claim/lock mechanism so duplicate workers or retries cannot process an event twice.
- Does not create regular activity merely to ask whether work exists.

Assess whether the existing `todoist_orphans` table should:
A) remain temporarily only for delete cleanup and later migrate,
B) be migrated into a clearly named generalized `todoist_sync_events` outbox,
or
C) be replaced outright.

Recommend one option and explain the migration path.

## Webhook requirements

Plan a Todoist webhook endpoint, for example:

POST /webhooks/todoist

It must include:

- Verification of Todoist’s webhook HMAC signature using server environment secrets.
- Fast success acknowledgment after verification and durable event capture.
- Explicit inbound delivery deduplication, not merely “the resulting local state is already correct.”
- A persistent webhook-event/audit model with:
  - provider event ID if available, otherwise deterministic payload fingerprint,
  - event type,
  - Todoist task ID,
  - payload hash or payload,
  - received timestamp,
  - processing status/result,
  - processed timestamp,
  - error details.
- Safe handling of repeated delivery.
- Lookup of both local `tasks` and local `eblasts` by Todoist task ID.
- Phase 1 handling of:
  - item completed,
  - item uncompleted,
  - item deleted.
- A way to prevent unnecessary outbound “echo” events after an inbound Todoist webhook updates the same local record.
- Clear handling for a webhook that references an unknown or already-unlinked Todoist task.

Also verify whether the existing Replit Todoist connector can be used alongside the required Todoist Developer App/webhook configuration. If that cannot be proven from repository code alone, identify it as an external setup spike rather than making an assumption.

## Reconciliation and observability

Even with webhooks, retain a controlled recovery path:

- Keep the existing batch endpoint or refactor it into an internal backfill/reconciliation service.
- It must not remain a normal user-facing “Push to Todoist” workflow.
- Propose an eventual Sync Health/Repair area that can show:

  - pending events,
  - failed events,
  - retry action,
  - unlinked tasks,

  - recent inbound/outbound activity,
  - optional manual “Sync now” repair action.
